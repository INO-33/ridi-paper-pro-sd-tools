# E70Q10 Android 8 eMMC 설치 계획 (2026-09-30)

**파티션 크기와 주소 확정(2026-10-01):**
[`EMMC_ANDROID8_FINAL_LAYOUT.md`](EMMC_ANDROID8_FINAL_LAYOUT.md)와
[`EMMC_ANDROID8_FINAL_LAYOUT.json`](EMMC_ANDROID8_FINAL_LAYOUT.json)을 최종
기준으로 사용한다. 실제 내부 eMMC는 8 GB급(7,818,182,656 B), 16 GB급은
외장 SD였다. system 1 GiB, vendor 256 MiB, cache 64 MiB, userdata 6,019 MiB,
boot/recovery 각각 32 MiB, 마지막 misc 4 MiB로 확정했다. 아래의 조사 이력과
여러 대안이 이 최종 배치를 대체하지 않는다. 실제 이미지 제작·기록은 별도 단계이다.

**2026-10-01 최신 권장안:** 사용자의 후속 지적에 따라 U-Boot와 p2 recovery를
모두 유지하고 p1만 51~83 MiB 구간으로 옮기는 안으로 수정했다. p3/EBR과
나머지 파티션을 재배치하면 가능하며, recovery 삭제는 필수가 아니다. 최신 검토는
[`INSTALL_REVIEW.md`](../../deliverables/emmc-20261001-review/INSTALL_REVIEW.md)에
있다. 기존 사용자 데이터 보존은 불필요하다는 조건에 따라 p4 FAT를 없애고
p7 data를 약 5.88 GiB로 통합하며 p9 misc 원본은 새 위치로 이전한다.
이 recovery 보존/data 통합안을 포함한 네 안 모두 오프라인 표 검증을 마쳤다.
부팅 진입과 원래 recovery 이미지 보존은 가능하지만 순정 recovery의 Android 8
마운트·초기화·업데이트 호환성은 별도 검증한다.

## 기준과 현재 상태

설치 대상은 시리얼 `PP1A1GK166561`이다. 기준 백업은
`/media/juwon/build/리디백업/backups/e70q10-PP1A1GK166561-20260923-full-emmc/`의
30개 `emmc.part??` 파일이다. 합계 7,818,182,656바이트(15,269,888섹터)이며,
동일 폴더에 eMMC boot0/boot1, 앞 19 MiB, EXT_CSD, 해시 기록이 있다.
7월 백업은 eMMC 용량과 파티션 표가 다른 기기의 상태이므로 이 기기에 복원하거나
그 폴더의 `restore_from_sd_in_recovery.sh`를 재사용하지 않는다.

9월 백업의 MBR/EBR을 직접 읽은 결과(섹터 크기 512바이트):

| 파티션 | 시작 섹터 | 섹터 수 | 확인한 상태 |
|---|---:|---:|---|
| p1 | 2,048 | 12,224 | 6 MiB 순정 Android boot image |
| p2 | 38,912 | 65,536 | 32 MiB 순정 recovery image |
| p3 | 104,449 | 7,547,618 | 확장 파티션 |
| p4 | 7,652,068 | 7,585,053 | FAT32, 약 3.62 GiB |
| p5 | 106,498 | 786,416 | ext4, 약 384 MiB |
| p6 | 894,962 | 786,416 | ext4, 약 384 MiB |
| p7 | 1,683,426 | 5,940,001 | ext4, 약 2.83 GiB |
| p8 | 7,625,475 | 16,368 | ext4, 라벨 `vendor`, 약 8 MiB |
| p9 | 7,643,891 | 8,176 | 라벨 `misc`, 약 4 MiB |

첫 19 MiB에는 U-Boot(0x400), hwcfg, NTX firmware, waveform, logo 및
p1 부트 이미지가 얽혀 있다. p1 뒤의 빈 공간처럼 보이는 구간에도 waveform과
logo가 있으므로 p1을 단순 확장할 수 없다. p2는 순정 recovery로 유지한다.
9월 U-Boot 바이너리에서 Android UIStyle의 정상 부팅 명령을
`booti ${fastboot_dev}`로 지정하는 ARM 코드를 확인했다. 실제 `booti`
코드 역시 파티션 번호를 조회한 뒤 그 시작 섹터로 MMC를 읽는다. 따라서
MBR에서 p1을 이동하는 방법은 바이너리 근거가 있지만 실기기 검증은 남았다.
상세 근거는 `deliverables/emmc-20260923-analysis/REPORT.md`에 있다.
9월 기기 U-Boot와 7월 추출본은 같은 Netronix U-Boot 2009.08 계열이다.
헤더상 실제 이미지 길이는 각각 236,840/236,832바이트로 8바이트 차이이고,
출력 문자열 1,463개 중 1,461개가 같다. 9월 이미지에서 8바이트 위치 차이를
보정하면 대응 구간의 약 97.7%가 동일하다. 따라서 별개 아키텍처로 취급하지
않되, 정확한 전체 이미지 제작에는 대상 기기의 9월 바이너리를 사용한다.

9월 23일 실행 기록에서는 `/system=/dev/mmcblk1p2`,
`/vendor=/dev/mmcblk1p3`, `/data=/dev/mmcblk1p4`였다. 즉 Android 8의
사용자 공간은 외장 SD에 있고, 현재 `fstab.E70Q10`도 SD 전용이다. eMMC의
p1에는 순정 커널(헤더상 3,902,844바이트)이 들어 있다. 현재 빌드의
`boot.img`는 11,771,904바이트, `system.raw.img`는 768 MiB,
`vendor.raw.img`는 256 MiB이다. 순정 p1·p5·p8에는 각각 들어가지 않는다.
`system.img`와 `vendor.img`는 Android sparse 형식이므로 기록 전 raw ext4로
변환해야 한다. 현재 제품 설정은 `TARGET_NO_RECOVERY := true`이다.

## 전체 eMMC 이미지 방식

가능하다. 9월 백업의 eMMC 사용자 영역 15,269,888섹터를 **정확한 바탕 이미지**로
삼고, 필요한 파티션 표와 Android 8 이미지만 오프라인에서 바꿔
`factory-emmc.img`를 만들면 된다. U-Boot, hwcfg, NTX firmware, waveform,
logo, 부팅 파티션과 misc의 보존 여부를 섹터별 manifest로 증명해야 한다.
eMMC의 별도 하드웨어 boot0/boot1 영역은 사용자 영역 이미지에 포함되지 않으므로
원본 백업과 해시를 설치 묶음에 함께 넣되, 변경하지 않는 한 다시 쓰지 않는다.
최종 이미지는 장치의 **같은 용량·같은 보드 구성**에만 적용한다.
9월 백업에는 기기 고유 정보와 기존 사용자 데이터가 포함될 수 있으므로 이
완성 이미지는 `PP1A1GK166561` 전용 복구/전환 산출물로 취급한다. 다른 기기에
배포할 범용 OS 이미지는 순정에서 필요한 바이너리만 선별하고 `/data`를 새로
초기화하며 기기 고유 영역을 각 기기에서 보존하는 별도 제작 방식이 필요하다.

이미지 제작은 백업 원본을 수정하지 않는 빌드로 한다. 입력 30개 파일과
각 산출물의 해시를 고정하고, 작업 복제본에 새 MBR/EBR과 raw ext4를 적용한
뒤 파티션별 범위와 전체 이미지 해시를 기록한다. 배포 묶음에는 전체 이미지와
분할 파일, 해시/크기/장치 식별 manifest, 설치기, 복원기를 둔다. FAT32 SD에
실을 경우 4 GiB 단일 파일 제한 때문에 분할 파일이 필요하다. 빈 영역까지
포함하는 7.82GB 전체 이미지는 안전한 복원 기준이지만 전송·쓰기 시간이 길다.
같은 배치를 파티션별 변경 이미지로 설치하는 빠른 경로는 이후에 만들 수 있다.

전체 이미지 자체는 부팅 문제를 해결하지 않는다. 새 부트 이미지의 커널만
10,027,968바이트라서 현재 p1의 6 MiB에 들어갈 수 없다. **p2 recovery는
번호·내용·기능을 보존한다.** 우선 검토할 방법은 MBR의 p1 항목을 더 넓은
새 위치(기존 p2 끝인 51 MiB 이후)로 옮기되 파티션 번호는 p1로 유지하는
것이다. 이렇게 하면 앞 19 MiB의 U-Boot/Netronix 영역과 기존 p2 recovery를
건드리지 않고 p1에 16~32 MiB를 줄 수 있다. 9월 U-Boot 바이너리의 Android
UIStyle 경로는 `booti`를 사용하고, 파티션 조회 결과의 시작 섹터를 읽는다.
따라서 p1 이동은 가장 유력한 경로이다. 다만 이동한 파티션의 실기기 부팅,
메모리 배치, recovery 및 fastboot 동작은 아직 확인되지 않았다.
그 전에는 p1 MBR 항목이나 recovery를 기록하지 않는다.
순정 recovery가 새 Android 8 파티션 배치를 안전하게 마운트·수리할 수 있다는
뜻은 아니므로, 복구 화면 진입과 원본 복원 기능을 따로 검증하고 독립 SD/USB
복구 환경도 유지한다.

**recovery를 포기하는 최소 부트 파티션 변경안:** 실제 `booti`는 정상 부팅 시
p1의 MBR 시작 섹터를 읽고, recovery 인자가 있으면 별도로 p2의 시작 섹터를
읽는다. 따라서 p1 항목을 기존 p2 자리인 섹터 `38912..104447`(32 MiB)로
옮기고 p2 항목을 비우면, p3/EBR을 이동하지 않고도 Android 8 부트 이미지를
담을 수 있다. 이 경우 기존 p2 recovery 내용을 새 부트 이미지가 덮으며
`booti mmc0 recovery`는 파티션 조회 실패가 예상된다. p5 system/p8 vendor의
용량 문제는 그대로여서 OS 전체 설치를 위해 별도의 재파티션은 필요하다.
이 안은 독립 SD/USB 복구 환경을 먼저 검증한 뒤에만 고려한다.

### 세컨더리 부트로더 판단

기술적으로 만들 수 있지만 현재의 우선 경로는 아니다. 순정 U-Boot의
`booti`/`bootm` 진입점에서 6 MiB p1의 작은 로더로 제어를 넘기고,
그 로더가 eMMC의 다른 위치에서 4.9 커널·DTB·램디스크를 읽어 Linux 부팅
규약에 맞게 넘겨야 한다. 여기에는 i.MX6SL MMC 초기화, 메모리 배치,
ATAG/DTB 전달, 캐시 상태, 전원 차단 후 재시도와 복구 키 동작의 별도 검증이
필요하다. 기존 U-Boot의 내부 함수를 안정적인 호출 인터페이스로 가정할 수 없다.
작은 Linux를 먼저 띄운 뒤 `kexec`하는 변형도 현 순정 3.0.35와 새 4.9.17
커널 구성 모두 `CONFIG_KEXEC`가 꺼져 있어 바로 사용할 수 없다.

판단 순서는 (1) 순정 U-Boot가 MBR에서 이동한 p1을 읽는지 실기기에서 검증,
(2) p1에 들어갈 수 있게 이미지를 줄일 수 있는지 확인,
(3) 두 방법이 실패하면 세컨더리 로더와 순정 U-Boot 수정 중 복구성과
구현량을 비교하는 것이다. 세컨더리 로더를
택해도 9월 eMMC 전체 백업과 독립 SD/USB 복구 설치기가 선행 조건이다.

### 설치 방식 후보

| 방식 | 적합한 용도 | 선행 조건 |
|---|---|---|
| 독립 SD 복구 환경에서 전체 이미지 기록 | 최초 전환, 완전 복원 | SD로 eMMC와 독립 부팅, 전체 백업·읽기 되검증, 중단 복구 |
| `fastboot boot`로 RAM 설치기 실행 후 SD/USB에서 분할 파일 읽기 | UART 없이 설치·진단 | 설치기의 eMMC 언마운트, 장치 식별, 충분한 저장/전원, 재시도 기록 |
| Fastboot 파티션별 flash | 검증 후 반복 배포 | 순정 Fastboot 파티션 매핑·크기·sparse 처리 증명; 첫 전체 전환에는 부적합 |

설치기는 실행 중인 Android의 `/system`이나 `/data`를 덮어쓰지 않고 독립
환경에서 동작해야 한다. 대상의 시리얼/CID/섹터 수를 검사한 뒤 입력 해시를
검증하고, 기록 후 읽기 해시와 파티션 표를 확인한다. 쓰기 중 전원 차단이
발생해도 같은 복구 환경으로 다시 진입하여 9월 이미지를 복원할 수 있어야
한다. 설치 완료 후에는 외장 SD를 제거하고 정상 전원 부팅을 시험한다.

## 결정 순서

1. **복구 기준 고정.** 9월 백업의 모든 부분 파일을 `SHA256SUMS`로 재검증하고,
   연결 스트림의 SHA-256을 `USERAREA_JOINED_SHA256`과 대조한다. 현재
   `CRITICAL_SHA256SUMS`에는 이동 전 `.partial` 절대 경로가 남아 있으므로
   경로를 현 위치로 치환해 별도 검증한다. boot0/boot1과 앞 19 MiB도 포함한다.
   복구 이미지는 실제 15,269,888섹터 장치와 시리얼/CID가 맞는지 확인하는
   독립 복구 환경에서만 사용한다. 7월 복구 스크립트의 기대 섹터 수는 다르다.
2. **상시 부팅 해법 확정.** 바이너리 분석으로 확인한 MBR 파티션 조회 동작을
   이동한 p1의 실기기 부팅으로 검증한다. 가능하면 p1 항목을 더 넓은 영역으로
   이동하고 p2는 원래 위치·내용으로 둔다. 이 경로는 정상 부팅과 recovery
   부팅의 실제 읽기 주소, 이미지 최대 크기, 전원 차단 후 재부팅을 증명해야
   한다. 불가능하면 커널과 램디스크를 6 MiB 이내로 줄이는 방안을 검토한다.
   U-Boot 교체나 세컨더리 부트로더는 별도의 마지막 설계 대상으로 둔다.
3. **eMMC용 이미지 분리.** 현재 SD용 `fstab.E70Q10`을 그대로 기록하지
   않는다. eMMC용 제품 설정에서 `/system`, `/vendor`, `/data`를 실제 새
   파티션에 맞게 바꾸고, 초기화·SELinux·암호화/검증 설정과 recovery/misc
   사용 여부를 함께 확인한다. SD용 빌드와 eMMC용 빌드의 산출물·해시를 구분한다.
4. **새 파티션 표 설계.** 부팅 해법이 정해진 후에만 섹터 단위 배치를 만든다.
   앞 19 MiB의 U-Boot/Netronix 자료, p2 recovery와 p9 `misc`의 내용 및 의미를 보존하고,
   p5 계열에 system 최소 768 MiB, vendor 최소 256 MiB, data와 필요한
   cache를 확보한다. p4 FAT의 기존 내용은 백업 대상으로 취급한다. MBR/EBR
   연결, 1 MiB 정렬, 실제 15,269,888섹터 끝 경계를 오프라인 이미지에서
   검증한다. 이 표는 아직 확정되지 않았다.
5. **기록 전 오프라인 리허설.** 9월 백업 복제본에 새 MBR/EBR과 raw ext4
   이미지를 적용하고 파티션 크기·중첩·파일시스템·부트 헤더를 검사한다.
   독립 복구 환경에서 eMMC가 마운트되지 않은 상태, 장치 CID와 용량,
   전원/접속 상태, 복원 경로를 확인한다. 현재 실행 중인 Android에서 자기
   eMMC를 재파티션하거나 전체 이미지를 복원하지 않는다.
6. **실기기 전환.** 위 검증이 끝난 뒤에만 외부 복구 환경에서 파티션과
   system/vendor를 기록하고 읽기 되검증한다. 부트 체인 변경은 마지막에
   수행한다. SD를 제거한 정상 전원 켜기, 반복 재부팅, `/system`·`/vendor`·
   `/data`의 실제 eMMC 마운트, 복구 진입, 전자잉크/터치/절전 동작을 확인한다.
   실패 시 9월 전체 백업으로 되돌릴 수 있어야 한다.

## 현재 결론

현재 Android 8 산출물은 **eMMC 직기록 가능 ROM이 아니다**. 가장 먼저 해결할
문제는 6 MiB 순정 부트 파티션과 11.8 MB 새 부트 이미지의 차이 및 U-Boot의
부트 위치 선택이다. 순정 U-Boot가 MBR에서 이동한 p1을 읽는다면 p2 recovery를
보존하면서 세컨더리 부트로더 없이 전체 이미지를 만들 수 있다.
이 문제가 해결되기 전에는 최종 파티션 섹터 표나
`fastboot flash` 명령을 확정하지 않는다. 본 문서는 조사와 설계만 기록하며
실기기 쓰기를 승인하거나 실행하지 않는다.
